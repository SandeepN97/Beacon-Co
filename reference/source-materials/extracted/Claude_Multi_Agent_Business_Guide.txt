1. Decide Which Claude Agent Approach to Use
1.1 Claude Projects: easiest, but mostly manual
Claude Projects are self-contained workspaces with project instructions, knowledge, and focused chats. They are useful
for creating separate role-based workspaces, such as Architect, Business Analyst, and Marketing Manager. However,
one project does not automatically execute a controlled handoff to another project. [1][2]
Strength Limitation
No coding required Handoffs normally require manual copying or a shared document
Each project has separate instructions and knowledge Not a strong orchestration system for software changes
Useful for role experimentation Permissions and tools are not as granular as Claude Code
subagents
Good for business research and writing Harder to enforce gates and independent review
1.2 Claude Code custom subagents: recommended
Claude Code custom subagents are specialized assistants stored as Markdown files with YAML frontmatter. Each agent
can have a separate system prompt, context window, tool allowlist, model, permission mode, skills, memory, hooks, and
other controls. Claude uses the agent description to decide when to delegate, and you can also invoke agents explicitly.
[3]
Why this matches your goal
You want each specialist to do one thing at a time. Subagents let you make the Architect read-only, allow the Code Writer
to edit files, prevent the PR Reviewer from changing code, and require structured handoffs between roles.
1.3 Agent teams and Agent SDK: advanced options
Agent teams coordinate multiple Claude Code sessions with shared tasks and inter-agent messaging, but the feature is
experimental and disabled by default. It is intended for coordinated parallel work, not as the first choice for a strict one-at-
a-time workflow. [4]
The Claude Agent SDK lets you build production agents in Python or TypeScript using the same agent loop and tools as
Claude Code. Use it after the manual subagent workflow is stable and you need repeatable automation, APIs,
schedules, external events, or audit reporting. [5]
Choose this When
Claude Projects You want to learn and manually test role prompts without coding.
Claude Code subagents You want controlled role separation, repository access, handoffs,
and software delivery.
Agent SDK You need a repeatable production service or integration with
your own application.
Agent teams You need several independent sessions to communicate and
work in parallel, and you accept experimental limitations.

2. Design Principles for Reliable Specialized Agents
One job per agent
Every agent should own one decision or deliverable, not an entire department.
Why: Prevents overlapping answers and unclear accountability.
Explicit inputs
State exactly what the agent is allowed to receive: approved requirements, architecture, code diff, test results, or business data.
Why: Keeps agents from inventing missing context.
Fixed output contract
Require a named deliverable and a standard handoff format.
Why: Makes the next agent easy to trigger and audit.
Limited tools
Give reviewers read-only tools; give editing and deployment tools only to roles that need them.
Why: Prompt instructions alone do not enforce permissions; tool rules do. [6]
Independent approval
No agent may approve its own work.
Why: Separates execution from verification.
Human gates
Humans approve business commitment, material architecture changes, legal risk, spending, and production deployment.
Why: Preserves accountability for high-impact decisions.
Sequential by default
Run one agent at a time until the workflow is trustworthy.
Why: Reduces conflicting edits, cost, and coordination failures.
Evidence over confidence
Require file references, test output, assumptions, and unresolved questions.
Why: Prevents polished but unsupported conclusions.
Stop conditions
Every agent must stop when its defined output is complete or a blocker is found.
Why: Prevents scope drift.
Least privilege
Default to read-only, then add the minimum required capabilities.
Why: Limits accidental or unauthorized changes.

5. Install and Prepare Claude Code
Anthropic currently documents native installers for macOS, Linux, WSL, and Windows PowerShell. After installation,
verify the CLI, sign in, enter the repository, and create a project-level CLAUDE.md. [7][8]
5.1 Install
macOS, Linux, or WSL:
curl -fsSL https://claude.ai/install.sh | bash
Windows PowerShell:
irm https://claude.ai/install.ps1 | iex
Alternative Homebrew installation:
brew install --cask claude-code
Verify and start:
claude --version
cd path/to/your/project
claude
5.2 Authenticate
 Most users: run claude, then use /login and approve the browser request.
 API usage: set ANTHROPIC_API_KEY in your shell before starting Claude Code.
 Enterprise cloud providers: configure Bedrock, Google Cloud, or the organization-approved provider according to
your administrator.
5.3 Initialize project context
/init
Claude Code can generate a CLAUDE.md that documents build commands, test commands, architecture, conventions,
and project constraints. Claude automatically reads relevant CLAUDE.md files. Keep the project-level file concise and
accurate, and commit it to version control for the team. [8]
Important
The first time you create a new .claude/agents directory during a running session, restart Claude Code if the new agent is
not detected. Existing watched directories update automatically when agent files change. [3]

7. Build Each Subagent File
A custom subagent file contains YAML frontmatter followed by a Markdown system prompt. Only name and description
are required, but useful controls include tools, disallowedTools, model, permissionMode, maxTurns, skills, MCP servers,
hooks, memory, effort, background behavior, worktree isolation, and display color. [3]
7.1 Minimal valid agent
---
name: code-reviewer
description: Reviews completed code changes for correctness, security, and maintainability. Use after
implementation and testing.
tools: Read, Grep, Glob
model: sonnet
permissionMode: plan
---
You are an independent code reviewer.
Review the completed changes and return findings with severity, evidence, impact, and recommendation.
Do not edit files. Stop after the review report.
7.2 Frontmatter fields you are most likely to use
Field Purpose
name Required unique lowercase identifier using letters and hyphens.
description Required. Explain exactly when Claude should delegate to this
agent.
tools Allowlist of tools available to the agent. Omit only when broad access
is intentional.
disallowedTools Explicitly removes tools from the inherited or specified tool set.
model Use an alias such as haiku, sonnet, opus, or inherit, subject to
availability.
permissionMode Common choices: plan for read-only planning/review; default for
controlled editing.
maxTurns Caps the number of agentic turns and limits runaway work.
memory user, project, or local persistent memory scope for cross-session
learning.
skills Preloads named skills into the agent context.
mcpServers Restricts the external MCP servers available to this agent.
hooks Adds lifecycle controls for the specific agent.
effort Overrides reasoning effort for that agent when supported.
background Forces background execution when true. Leave unset for strict
sequential control.
isolation Use worktree for an isolated Git checkout when parallel editing is
necessary.
7.3 How to write a strong description
Weak Strong
Helps with architecture Creates a technical architecture from approved requirements. Use
after product scope is approved and before implementation.

8. Configure Permissions, Safety, and Tool Access
Claude Code permissions are enforced by the application rather than by prompt wording. Use permission rules, modes,
and hooks to control actual capabilities. [6]
8.1 Recommended tool matrix
Role type Typical tools Hard boundary
Chief of Staff Read, Glob, Grep No editing or deployment
Program / Business / Product Read, Glob, Grep No source edits
Architects and reviewers Read, Glob, Grep; optional read-only Bash No Write or Edit
Market Researcher Read, Glob, Grep, WebSearch, WebFetch No edits to product code
Codebase Researcher Read, Glob, Grep, read-only Bash No Write or Edit
Code Writer Read, Glob, Grep, Write, Edit, Bash No merge or production deployment
QA Engineer Read, Glob, Grep, Bash Do not change tests to hide failures
DevOps Engineer Read, Glob, Grep, Write, Edit, Bash Production commands require explicit human
approval
Release Manager Read, Glob, Grep, Bash No release execution
8.2 Permission modes
Mode Use
plan Read and explore without editing source files. Best for architects and
reviewers.
default / manual Prompts for tool permissions as needed. Best general mode for
controlled work.
acceptEdits Automatically accepts edits in the approved working area. Use only
after the workflow is trusted.
dontAsk Denies tools unless they are pre-approved. Useful for tightly
controlled headless agents.
auto Uses background safety checks to approve aligned actions; validate
carefully before relying on it.
bypassPermissions Skips most prompts and gives broad access. Avoid for normal
business workflows.
Security rule
Never use bypassPermissions for an agent that has production credentials, destructive infrastructure access, customer
data, or broad filesystem access. Prefer explicit allow and deny rules plus human approval.

9. Create the Chief of Staff Orchestration Layer
The Chief of Staff is responsible for routing and control, not for doing specialist work. It should inspect the request, select
the next agent, validate the previous handoff, and stop at approval gates.
9.1 Master orchestration prompt
Act as the Chief of Staff for this organization.
Use project subagents and run them strictly one at a time.
Never perform a specialist's deliverable yourself when the specialist exists.
Never start the next agent until the current agent returns the universal handoff.
Default workflow:
1. program-manager
2. market-researcher when the opportunity is unvalidated
3. business-analyst
4. product-manager
5. ux-designer when user-facing behavior changes
6. solution-architect
7. security-architect
8. codebase-researcher
9. code-writer
10. qa-engineer
11. pr-reviewer
12. devops-engineer when delivery configuration changes
13. release-manager
Rules:
- If an agent reports a blocker, stop and report it.
- Do not let an agent approve its own work.
- Do not run agents in parallel unless I explicitly authorize it.
- Require human approval before material architecture changes and production release.
- Preserve every agent's assumptions, risks, and unresolved questions.
- Return work to the owning agent when a reviewer finds a defect.
- Do not allow scope expansion without Product Manager and human approval.
At the end, provide:
- Current phase
- Completed gates
- Blockers
- Pending approvals
- Recommended next action

9.3 Sequential execution instruction
Run the workflow in the foreground and strictly one agent at a time.
Do not use background execution.
Do not start the next agent until the current result is required and reviewed.
When invoking an agent, include only the approved input package for that stage.
Current behavior to understand
Recent Claude Code versions may run subagents in the background by default when Claude decides it can. A strong
sequential instruction and explicit foreground invocation are important for your workflow. The background field should
remain unset rather than forced true. [3]

10. Run, Test, and Improve the Agent Organization
10.1 First dry run
Use the controlled agent workflow for this request:
Create a customer complaint management application where employees can register complaints, attach documents,
assign an owner, track status, record resolution notes, and produce management reports.
Begin with program-manager. Run one agent at a time. Stop after Business Analyst and Product Manager complete
their deliverables so I can review the scope.
10.2 Test each agent separately
Test Expected behavior
Boundary test Ask the Architect to write code. It should refuse and return
architecture only.
Permission test Ask the PR Reviewer to edit a file. The tool configuration should
prevent editing.
Missing-input test Invoke Code Writer without approved requirements. It should stop
and name the missing gate.
Handoff test Verify every required handoff field is present.
Reviewer independence test Create a deliberate defect and confirm QA or PR Reviewer reports it
rather than hiding it.
Scope test Ask for an unrelated feature during implementation. Code Writer
should flag scope expansion.
Safety test Try a destructive or production command in a non-production
sandbox and verify rules block or ask.
Cost test Run the same task with different model assignments and compare
result quality and usage.

11. Scale to Agent SDK, Integrations, and Agent
Teams
11.1 When to use the Agent SDK
 You need an API or internal application to trigger workflows.
 You need repeatable runs with structured logs and results.
 You need schedules, webhooks, queues, or event-based automation.
 You need integration with CRM, ticketing, GitHub, Slack, databases, or business systems.
 You need centralized cost controls, approvals, and audit reporting.
The Agent SDK supports production agents in Python and TypeScript with built-in tools and filesystem-based Claude
configuration. [5]
11.2 When to use MCP
Model Context Protocol connections expose approved external tools and data to Claude. Scope MCP servers to the
agents that need them, such as giving the Sales Agent access to CRM while withholding it from Code Writer. Do not give
all agents every connector.
Agent Possible integration Restriction
Sales Strategist CRM Read leads; require approval before sending
customer messages
Customer Support Ticketing and knowledge base No source-code or billing changes
Program Manager Project tracker Create or update tasks only within approved
project
PR Reviewer GitHub read access No merge or write access
Finance Analyst Accounting or billing data Read-only and minimum necessary data
Knowledge Manager Document repository Controlled write access with version history
11.3 When to use agent teams
Agent teams are useful when multiple independent sessions must communicate and coordinate a shared task list. They
are not necessary for the sequential workflow in this guide, and Anthropic currently labels them experimental. [4]
Use subagents when Use agent teams when
One main session delegates focused work and receives results Teammates must communicate directly and coordinate shared tasks
You want a strict sequence You want parallel work with a lead
Work is small enough for one session to coordinate Work is divided into independent components or research tracks
You want lower operational complexity You accept experimental limitations and increased token usage
11.4 Cost-control rules
 Use stronger models for high-impact architecture, security, and difficult analysis; use faster models for routine
search and formatting.
 Cap maxTurns for every agent.
 Do not run duplicate reviewers unless the risk justifies it.
 Summarize large exploration in a Codebase Researcher rather than repeating it in every agent.
 Store stable project context in concise files rather than re-sending it manually.

14. Rollout Checklist and Troubleshooting
14.1 Four-stage rollout
Stage Exit requirement
Stage 1: Design Create CLAUDE.md, 14 agent files, universal handoff, permissions,
and approval gates.
Stage 2: Sandbox Run small non-production examples; test boundaries, permissions,
handoffs, and reviewer independence.
Stage 3: Pilot Use the workflow on one real low-risk project with full human review
and cost tracking.
Stage 4: Controlled automation Automate only stable steps; add MCP, SDK, schedules, or
parallelism where evidence supports it.
14.2 Go-live checklist
 [ ] Every agent has one responsibility and a clear description.
 [ ] Every agent has a defined input, output, stop condition, and next handoff.
 [ ] Reviewers lack Write and Edit tools.
 [ ] Deployment and destructive commands require explicit approval.
 [ ] The repository has accurate build, test, and run commands in CLAUDE.md.
 [ ] All 14 core agents pass boundary and permission tests.
 [ ] A human owns each approval gate.
 [ ] The team knows how to stop a workflow and recover from a bad change.
 [ ] Costs and model usage are measured.
 [ ] Customer, legal, security, and privacy data access follows least privilege.
14.3 Troubleshooting
Problem Fix
Claude cannot find an agent Confirm the file is in .claude/agents/ or ~/.claude/agents/, the YAML
is valid, and the name is unique. Restart if the agents directory was
created after the session began.
Wrong agent is selected Rewrite the description with the exact trigger and role boundary;
invoke the desired agent explicitly while testing.
Agent can edit when it should not Remove Write/Edit, use plan mode, add deny rules, and test the
actual permission behavior.
Agent ignores the handoff Make the handoff mandatory near the end of the system prompt and
define the stop condition.
Agents duplicate work Move discovery into Codebase Researcher or Market Researcher
and pass only the summarized evidence forward.
Context becomes inconsistent Use a Knowledge Manager, decision records, and clear superseded-
document labels.
Parallel changes conflict Return to sequential execution or use isolated worktrees with strict
file ownership.
Workflow is too expensive Reduce passes, shorten prompts, cap turns, use cheaper models for
routine tasks, and measure cost per accepted outcome.
An agent makes unsupported claims Require file references, test output, sources, assumptions, and
confidence limitations.
A reviewer finds a blocker late Move that review earlier: security design before code, test design
before implementation, data review before migration.
